// 03 — AI INFERENCE ENGINE

Producer-Consumer Threading + YOLOv8s ONNX

The AI engine is the heart of the system. It runs on the laptop and solves a fundamental problem: the ESP32 video stream is slow and compressed, but AI inference is CPU-heavy. A naive approach causes choppy video. The solution is two parallel threads working independently.

THE CORE PROBLEM IT SOLVES
If you run YOLOv8s on every frame, the video stutters because inference is slow (~8 FPS). If you skip frames to speed up video, the AI misses detections. The Producer-Consumer architecture solves this by making video and AI completely independent.
// ARCHITECTURE — TWO SEPARATE THREADS
# THREAD 1 — FrameGrabber (Producer)
# Runs as fast as possible, always reading
# Drains the network buffer continuously
while running:
    ret, frame = cap.read()     # Always reading
    with lock:
        latest_frame = frame    # Overwrite old frame

# THREAD 2 — Main (Consumer)
# Runs inference only 8 times/second
if (now - last_inference) >= 0.125:
    frame = latest_frame        # Grab latest only
    results = model.predict(frame)  # Heavy AI work

// TEMPORAL SMOOTHING — FALSE POSITIVE ELIMINATION
WHY THIS EXISTS
A single AI frame can be wrong. A shadow, a jacket on a chair, a cat — these can fool the model for one frame. If we push an alert to Firebase every time the model says "yes", the dashboard will flash constantly. Temporal smoothing requires the model to agree across multiple frames before treating it as a real detection.

// 04 — CLOUD LAYER

Firebase Realtime Database — The Universal Bus

Firebase RTDB is the synchronization backbone. It acts as a shared memory space between the Python AI engine and the web dashboard. The Python script writes to it via REST API. The dashboard reads from it via persistent WebSocket listeners that fire the moment data changes.

rob-track-default-rtdb └── bot1/ ├── ai/ ← Python writes here ├── personDetected: true/false ├── confidence: 85 (integer 0–100) └── timestamp: "14:22:05" ├── gps/ ← Phase 2 (empty now) ├── latitude: null ├── longitude: null ├── satellites: null └── timestamp: null ├── radar/ ← Phase 2 (empty now) └── presence: null └── camera/ ← Phase 2 (empty now) └── stream_url: null
IMPORTANT — CONFIDENCE FORMAT
Python stores confidence as an integer 0–100 (e.g., 85 means 85%). The dashboard divides by 100 before displaying (85 → 0.85). This is intentional — Firebase doesn't support decimals reliably at high write frequency.

// 06 — SWARM INTELLIGENCE CONCEPT

Why Swarm? The Design Philosophy

Traditional surveillance uses a single camera or robot. SENTINEL uses multiple coordinated agents — a swarm — where each bot operates independently but contributes to a unified intelligence picture. If one bot fails, the others continue. This is the core IEEE research contribution.

PROPERTYSINGLE ROBOTSENTINEL SWARM
CoverageOne area onlyMultiple zones simultaneously
Failure toleranceTotal system failureOthers continue operating
ScalabilityFixed — can't expandAdd bots = more coverage
Response timeMust travel to eventNearest bot responds
CoordinationNoneFirebase shared state
Cost per unitHigh — one powerful botLow — many simple bots
THE SWARM ARGUMENT FOR IEEE
The paper argues that many simple, intelligent units outperform one complex unit. Each bot needs only to see its local area and report findings. Intelligence emerges at the cloud layer where all bot data converges. This mirrors how ant colonies, bird flocks, and military drone swarms operate.
NO SINGLE POINT OF FAILURE
If BOT-03 crashes, BOT-04 keeps patrolling its zone. If the laptop running inference goes down, bots continue streaming and radar keeps detecting. The system degrades gracefully rather than failing completely.

// 07 — COMPLETE DATA FLOW

End-to-End Signal Journey

Follow a single detection event from the moment a person enters the camera frame to the moment the dashboard shows THREAT. Every step is explained so you can answer any question from a judge about exactly how data moves through the system.

①
PERSON ENTERS CAMERA FIELD OF VIEW
The ESP32-CAM's OV3660 sensor captures the scene. The image is compressed to JPEG at quality 25 and streamed as MJPEG over Wi-Fi on port 81. The hostname sentinel.local (mDNS) means no IP address needs to be known.
http://sentinel.local:81/stream → MJPEG frames
HARDWARE
②
FRAMEGRABBER THREAD CATCHES THE FRAME
Thread 1 (FrameGrabber) continuously calls cap.read() to drain the network buffer. It stores only the latest frame in a thread-safe Lock. Old frames are immediately overwritten — we never queue frames, only keep the freshest one.
threading.Lock() → latest_frame (always fresh)
PYTHON THREAD 1
③
MAIN THREAD GRABS FRAME FOR INFERENCE (8×/sec)
Every 125ms, the main thread reads the latest frame from the Lock. It resizes it to exactly 640×480 VGA for the model. This timing is controlled by comparing timestamps — if not enough time has passed, it skips and just renders video.
if (now - last_inference) >= 0.125s → run YOLOv8s
PYTHON MAIN THREAD
④
YOLOv8s ONNX ANALYSES THE FRAME
The model scans the 640×480 frame for Class 0 (Person). It outputs bounding boxes with confidence scores. Only detections with confidence ≥ 0.70 are kept. Agnostic NMS removes overlapping boxes. The result is a list of confirmed human positions.
model.predict(frame, classes=[0], conf=0.70, agnostic_nms=True)
AI INFERENCE
⑤
TEMPORAL SMOOTHING DECIDES IF IT'S REAL
The detection result (true/false) is pushed into a deque of the last 5 frames. If 3 or more of the last 5 frames say "person detected", it is confirmed as a stable detection. A single frame saying yes is NOT enough — this eliminates flickering false positives.
deque(maxlen=5) → sum >= 3 → stable = True
SMOOTHING
⑥
STATE CHANGE TRIGGERS FIREBASE PUSH
Firebase is ONLY written to when the stable detection state CHANGES — from CLEAR to THREAT, or THREAT to CLEAR. This prevents spamming Firebase with thousands of identical writes per minute. One clean write per state change.
if stable != was_stable → firebase_push("bot1/ai", {personDetected, confidence, timestamp})
FIREBASE WRITE
⑦
DASHBOARD LISTENER FIRES INSTANTLY
The dashboard has a persistent WebSocket connection to Firebase via onValue('bot1/ai'). The moment Firebase receives the write in step 6, this listener fires on the browser — sub-second latency. The AI Threat panel updates, the confidence bar animates, and if confidence ≥ 70 the threat card turns red.
fbDb.ref('bot1/ai').onValue(snap → updateThreatPanel(snap.val()))
DASHBOARD UPDATE
⑧
OPERATOR SEES THREAT — TOTAL LATENCY ~400ms
From the moment the person enters frame to the moment the dashboard shows THREAT: ~125ms for frame capture interval + ~80ms for ONNX inference + ~50ms for Firebase propagation + ~50ms for browser render. Total end-to-end latency is approximately 300–500ms. Well within real-time surveillance requirements.
Total: ~400ms frame-to-alert latency

// HOW TO EXPLAIN THIS TO A JUDGE — SIMPLE VERSION
IF THEY ASK: "HOW DOES THE AI WORK?"
We use YOLOv8s — a neural network trained on 80,000 images to recognize humans. It runs on the laptop because the ESP32 is too weak for AI. The camera sends video wirelessly, Python captures it, runs the model 8 times per second, and if it sees a person with 70% or more confidence it sends an alert.
IF THEY ASK: "WHY TWO THREADS?"
One thread does nothing but grab video frames continuously so the stream stays smooth. A second thread does the heavy AI work 8 times per second. Without this separation, running AI on every frame would cause the video to freeze — it's like having one worker drive the car while another reads the map.
IF THEY ASK: "WHY FIREBASE?"
Firebase is our real-time message bus. The Python script writes detection results to it. The dashboard reads from it. They never talk directly to each other — Firebase sits in the middle. This means we could have 100 dashboards on 100 computers all showing the same live data simultaneously.
IF THEY ASK: "WHAT'S NOT INTEGRATED YET?"
The radar, GPS, and motors are planned for Phase 2. The current system demonstrates the core AI vision pipeline end-to-end. The dashboard shows simulation for these sensors, clearly labeled. Our contribution is the Producer-Consumer architecture, ONNX optimization, and temporal smoothing — all of which are fully working.
